# 在线对决代码审查与风险清单

审查日期：2026-09-15。基准：本地工作区，包含本轮联机边界修补。

本次检查 `game/online_game`、复用的战斗引擎/UI 和现有联机测试。本文同时记录已实施的修复、仍需双机验证的风险，以及线上部署与本地代码可能不一致的地方。

证据分为：**已复现**（本地 Node/VM 模拟得到异常结果）、**代码确认**（实现中存在明确缺口）、**待双机验证**（存在竞争或边界风险，实际发生频率尚未测量）。本次没有连接真实玩家、修改 Worker 或进行生产压测。

## 2. 数据与行动权限

### 2.1 客机收到房主手牌（P0，已复现）

位置：[online_session.js](../../online_game/online_session.js) 的 `_broadcast()`；[online_ui.js](../../online_game/online_ui.js) 的 `startMatch()`。

- 修复前每次状态消息同时发送 `hostState` 与 `guestState`，开局包也同时包含两份快照；本地截获的 `hostState.playerHand` 示例长度为 2。
- 修复后 `OnlineHostSession._broadcast()`、开局包和错误包只发送 `guestState`；房主快照只留在房主会话内，需用真实抓包再次验收。

基本应对：发送前只构造接收者的快照，房主快照留在房主内存中。建立字段白名单，审计初始状态、普通更新、错误响应、判定数据和事件包。测试应检查实际发出的完整消息，而不仅断言 `guest.aiHand === null`。

### 2.2 权威引擎允许绕过出牌步骤（P0，已复现）

位置：[online_match.js](../../online_game/online_match.js) 的 `dispatch()`；[engine.js](../../js/combat/engine.js) 的 `dispatch()`、`chooseSuperPurifyTarget()` 等入口。

- 修复前联机层把任意 `method/params` 直接交给单机入口；未打净化牌也能提交 `choosePurify`，灼烧会被错误清除。
- 修复后 `COMMANDS` 白名单、行动者/阶段/待决策校验和 `GAME_OVER` 拦截位于 `OnlineMatchHost._validateCommand()`；非法指令不进入引擎且不会改状态。
- 后续仍需把每个新增技能决策加入矩阵测试，避免只修复公共入口而漏掉角色专属分支。

基本应对：建立在线动作白名单，逐项校验 `actor + phase + decisionId + params`。净化必须绑定真实待处理决策；牌索引/牌 ID、目标、颜色、排序索引都要校验。非法指令不得修改状态或清掉尚未完成的决策。重新开局由大厅状态机处理。

### 2.3 客机选中对手牌后不能确认（P1，已复现）

位置：[online_match.js](../../online_game/online_match.js) 的 `project('guest')`；[controls.js](../../js/ui/controls.js) 的 `_renderControls()`。

- 修复前客机投影无条件清空 `state.selectedAICard`；Chan 7 选择索引 0 后内部值为 0，但客机快照变为 -1，确认按钮保持禁用。
- 修复后只有非行动方隐藏临时选择；当前行动者的选择索引会保留并随版本化快照返回。

基本应对：选择状态绑定决策拥有者；当前行动者保留有效索引，旁观方清空。不要因为观察视角是 guest 就清空。回归测试必须覆盖房主与客机分别使用 Chan 4/7、Moze 5、Saiki 3 等选择对手牌的完整流程。

### 2.4 Chan 排序弹窗仍可能出现在双方（P1）

位置：[online_match.js](../../online_game/online_match.js) 的 `project()`；[hand_render.js](../../js/ui/render/hand_render.js) 的 `_renderPlayerHand()`；[dialogs.js](../../js/ui/dialogs.js) 的 `showChanFiveDialog()`。

- 修复前非行动方快照仍包含 `chanFiveCards`，手牌渲染也只检查数组长度，可能双方同时出现排序弹窗。
- 修复后 `project()` 仅向当前行动者投影 Chan 5 数据，手牌渲染检查 `onlineCanAct`，`syncCombatDialog()` 会清理过期排序窗；仍需双端 UI 验收。

基本应对：统一由决策描述驱动所有弹窗，例如 `{ id, type, actorId, choices }`；仅拥有者收到私有 choices 并创建弹窗。净化、排序、选目标、选颜色采用同一套权限与销毁流程。

## 3. 回合与技能适配

### 3.1 回合开始的中毒、角色被动遗漏（P1，已复现）

位置：[online_match.js](../../online_game/online_match.js) 的 `_installHooks()`；[engine.js](../../js/combat/engine.js) 的 `turnStart()`。

- 修复前 `startAITurn()`/`aiTurn()` 只切换阶段，不执行新进攻者的 `turnStart()`；客机 Ryan 生命 50、中毒 2 的回合开始后仍为 50。
- 修复后在线钩子在实际行动者确定后调用一次 `turnStart()`；本地回归为 49（中毒 2、Ryan 被动恢复 1），先手为客机的构造路径也已覆盖。

基本应对：统一 `beginTurn(actorId)`，先确定实际先手，再触发一次回合开始效果。将“防御完成后继续进攻”与“进入新回合”分开，避免修补时重复触发被动。对房主/客机互换、双方先手分别测中毒、Ryan 恢复、Chan 抽牌。

### 3.2 交换 player/ai 引用依赖手工字段清单（P1，待针对技能验证）

位置：[online_match.js](../../online_game/online_match.js) 的 `swapParticipants()`、`projectEvents()`、`project()`。

当前仅交换部分顶层字段和少量嵌套目标。新增按参与者索引的数据，如 `bombPlayTokens`、延迟状态、私有判定、复合目标，都可能遗漏。事件投影也主要交换已知顶层字段。

基本应对：核心结算逐步使用稳定的 `participantId`；UI 边界才映射成“自己/对手”。过渡期集中声明所有归属字段，增加交换两次恢复原值的测试，以及双方使用同一技能所得结果互为镜像的测试。这里是扩展风险，不应据此认定所有相关技能当前都已出错。

## 4. 消息同步与会话生命周期

### 4.1 重复请求、过期快照都被接受（P1，已复现）

位置：[online_session.js](../../online_game/online_session.js) 的 `handleCommand()`、`receiveState()`；[events.js](../../js/ui/events.js) 的 `_consumeEvents()`。

- 修复前 `requestId` 只用于匹配 Promise；同一个 `requestId=7` 的选牌请求执行两次，选中索引从 0 变回 -1。客机先收到回合 8、再收到回合 3 时也会回退，事件 ID 只在单次消费中去重。
- 修复后房主按“参与者+请求 ID”缓存结果，客机拒绝较小的 `stateVersion`，UI 按局保存已消费事件 ID；重复请求返回相同结果。

基本应对：消息携带 `protocolVersion / matchId / requestId / expectedStateVersion`，响应携带单调递增的 `stateVersion`。房主按“本局+参与者+请求 ID”缓存处理结果，重复请求返回原结果；客机拒绝旧快照。事件 ID 按局记录消费进度。不能用回合数替代版本号，因为同一回合有多次动作。

### 4.2 请求无响应会永久等待（P1，代码确认）

位置：[online_session.js](../../online_game/online_session.js) 的 `OnlineGuestSession.dispatch()`；[online_ui.js](../../online_game/online_ui.js) 的连接事件处理。

修复前 `send()` 返回成功后只将 Promise 放入 `_pending`，没有超时；响应丢失时操作锁可能一直保留。当前已加入 12 秒请求超时、传输关闭提示和 pending 清理，但完整断线恢复仍未实现。

基本应对：增加有界请求超时，显示“连接中断/正在核对操作结果”。重试时沿用原请求 ID，并先完成 4.1 的去重。统一处理传输失效，暂停操作并清理或挂起等待中的请求。

### 4.3 开局确认尚未构成同步屏障（P1，时序待双机验证）

位置：[online_ui.js](../../online_game/online_ui.js) 的 `startMatch()`、`_sendMatchStart()`、`_handlePeerMessage()`。

修复前房主先挂载战斗界面再发开局包，可在客机确认前操作；开局包 ack 也没有绑定 matchId。当前 `OnlineMatchHost.started=false` 会锁住双方操作，客机确认带 matchId 后房主发送 `matchReady`，双方再开放各自投影；重试 12 次仍无确认时会向客机发送失败原因并回到房间。

基本应对：使用 `STARTING → START_ACK → IN_BATTLE` 流程，双方确认相同初始快照后才开放操作；超时保留可重试状态并显示原因。补发开局后同步最新快照，不能把已进行的对战恢复成最初状态。旧局 ack 不得确认新局。

### 4.4 刷新、离开、再战缺少完整结束/恢复路径（P1）

位置：[online_ui.js](../../online_game/online_ui.js) 的 `peerLeft`、`close`、`_destroySharedBattle()`、`_resetToLobby()`；[p2p_adapter.js](../../online_game/p2p_adapter.js) 的 `close()`。

- 代码确认：没有重连身份、快照恢复或房主迁移；刷新会丢失本地战斗会话。
- 对手离开仅更新房间提示，而 `renderRoom()` 在战斗期间提前返回，战斗面板可能仍显示等待。
- 旧动画风险：将 `_battleAnimation` 赋值为新的 Promise 不会取消已排队任务；任务运行时访问 `this.battleUI`，可能在返回大厅后访问空对象，或在再战后写入新 UI。
- `_destroySharedBattle()` 没有完整取消弹窗、动画、UI 回调和计时器；`pendingSync` 也未统一按局清理。

基本应对：小规模阶段先做确定的断线提示、暂停/结束和返回大厅路径；不支持恢复时明确告诉玩家本局结束。之后再加限时重连令牌、最近快照和事件进度。每局使用独立 matchId/取消信号，退出时销毁会话拥有的任务和弹窗，旧局结果直接丢弃。

### 4.5 两套更新队列可能互相覆盖（P1，待双机验证）

位置：[online_ui.js](../../online_game/online_ui.js) 的 `_queueSharedBattleResult()`；[controls.js](../../js/ui/controls.js) 的 `_apiAction()`；[hand_render.js](../../js/ui/render/hand_render.js) 的点击回调。

远端主动推送通过 `_battleAnimation` 排队，本人动作通过 `_apiAction()` 更新，单击选牌又直接 `_sessionDispatch()`。三条路径没有共同的快照版本和串行应用入口。低延迟同机测试可能正常，延迟、快速选牌或动画未结束时可能回写旧状态。

基本应对：让所有结果进入同一个“验证版本→应用快照→播放事件”的入口；动画不拥有权威状态。纯 UI 选择尽量留在本机，真正出牌时提交稳定的 cardId 和状态版本，避免索引随着抽牌/交换变化。

## 5. 房间与传输层

### 5.1 peerId 冲突与大厅消息身份信任（P1）

位置：[worker.js](../../online_game/signaling/worker.js) 的 hello/roomMessage 分支；[online_ui.js](../../online_game/online_ui.js) 的 `_handleRoomMessage()`、`_upsertPlayer()`。

- 修复前 Worker 接受客户端提供的 peerId；相同 ID 会覆盖 Map。大厅载荷也可以声称属于另一位玩家。
- 修复后 Worker 为每条连接生成 peerId，helloAck 后客户端采用服务端身份；lobbyUpdate 由连接元数据重写，UI 还会校验 `from`，并移除未带发送者身份的重复 DataChannel 大厅更新。重连令牌仍待补充。

基本应对：Worker 分配唯一连接身份和角色，helloAck 后客户端采用服务端身份；重连另用短期令牌。大厅消息的发送者以连接元数据为准，拒绝修改另一方昵称、角色和准备状态。删除连接前确认 Map 中保存的 socket 就是正在关闭的 socket。

### 5.2 房间中的重试按钮无效（P2，已复现）

位置：[online_ui.js](../../online_game/online_ui.js) 的 `connect()`、`renderRoom()`。

修复前“重试连接”调用 `connect(this.role)`，会从已经卸载的入口页读取字段，导致“请先填写昵称”。

当前已将连接参数作为对象传入，并从会话保存的 nickname/roomCode/signalUrl 重试；仍需补连接代次校验，避免旧 peer 回调覆盖新连接。

### 5.3 P2P/信令回退的交付语义不完整（P2）

位置：[p2p_adapter.js](../../online_game/p2p_adapter.js) 的 `send()`、`_sendSignal()`、`_onSignal()`。

- DataChannel 与 WebSocket 各自有消息顺序，切换通道时没有跨通道序号，不能保证应用级统一顺序。
- 修复前 `_sendSignal()` 异常仍可能被外层视为成功，DataChannel 没有缓冲阈值，Worker 也会把中继包回送给发送方。
- 当前发送返回值反映入队/发送结果，DataChannel 设置 256 KiB 背压，信令按 server peerId 排除发送方；跨通道序号和确认仍待补充。
- STUN 配置只有一个入口；没有 TURN。当前已有 WebSocket 游戏消息回退，仍需测试完全无法 P2P 的完整对局。

基本应对：先实现局 ID、序号、ack 和去重，再完善通道切换。让 send 的返回值准确反映是否入队成功，设置缓冲阈值和队列上限；合并选牌等高频非关键更新。确认中继包不回送发送方。小规模阶段可继续使用现有中继，不必把引入 TURN 当成上述协议问题的解决办法。

### 5.4 信令服务缺少资源与握手保护（P2，代码确认）

位置：[worker.js](../../online_game/signaling/worker.js)、[wrangler.jsonc](../../online_game/signaling/wrangler.jsonc)。

- 修复前两人限制只在 hello 后发生，没有握手超时；大小检查使用字符串长度，也没有消息频率限制或心跳清理。
- 当前已加入 15 秒 hello 超时、UTF-8 字节上限、基础 10 秒/240 条限流、可选 Origin 白名单和 close 时清理；房间 TTL、令牌和更细粒度配额仍待补充。

基本应对：增加握手超时、字节长度校验、消息结构白名单、连接/发送频率限制和有界队列；统一清理心跳和房间。Origin 可作浏览器来源限制，但不能替代身份认证。监控活跃连接、关闭原因、消息大小及中继比例。

## 6. 大厅、公平性与发布

### 6.1 角色暗选只是界面隐藏（P2，代码确认）

位置：[online_ui.js](../../online_game/online_ui.js) 的 `_sendLobbyUpdate()`、`playerMarkup()`。

准备前就发送完整 character 名称，UI 仅显示“已选择角色”。若需求是严格暗选，对手仍能读取消息提前获知选择。

基本应对：先发送“已选/已准备”，锁定后再揭示角色；需要更强公平性时采用“角色+随机盐”的哈希承诺与揭示流程。两端和服务端都验证角色属于允许的主角列表。

### 6.2 房主权威的信任范围（架构限制）

房主浏览器保存完整引擎、双方手牌、牌库及随机结果，客机信任房主快照。因此即使修复客机越权与手牌泄露，也不能阻止房主修改自己的 JS 或随机结果。

基本应对：当前可定位为熟人对战/测试模式。记录规则版本和可回放指令有助排查错误；固定随机种子有助复现，但不能证明房主诚实。若将来需要排名或奖励公平性，再评估可信服务端结算。此项是架构决策，不是添加一个前端校验就能解决的 bug。

### 6.3 缺少版本协商与原子发布（P2）

位置：[index.html](../../online_game/index.html)、[online_config.js](../../online_game/online_config.js)、联机消息定义。

大量脚本独立加载，仅部分资源有版本 query；协议中没有规则版本/构建版本握手。旧页面与新页面对战时，可能出现新字段丢失、按钮不识别和技能行为差异。

基本应对：握手交换 protocolVersion/buildId/rulesVersion，不兼容时在准备前要求刷新。静态资源采用统一构建版本或内容哈希，HTML 使用合适的更新策略，保留可回滚版本。`/health` 只说明健康接口可访问，不证明建房、WebSocket、中继和完整对局都正常。

## 7. 建议的最小结构调整

继续复用单机 UI 和规则引擎即可，先收紧边界，无需重写整套游戏：

| 模块建议 | 职责 |
| --- | --- |
| `protocol.js` | 统一消息格式、版本、matchId、requestId、stateVersion |
| `command_validator.js` | 动作白名单、阶段/决策拥有者、目标和参数校验 |
| `state_projector.js` | 公共状态与个人私有数据；统一参与者视角映射 |
| `decision_controller.js` | 选牌、净化、排序、选色的拥有者、生命周期与 UI 接口 |
| `match_lifecycle.js` | 开局确认、断线、结束、再战、旧任务取消 |
| 现有 `online_session.js` | 请求去重、超时、快照版本、统一结果应用 |
| 现有 `p2p_adapter.js` | 有界传输、错误状态、通道选择；不直接决定游戏规则 |

推荐实施顺序：

1. 修正私有数据泄露、远端动作校验、客机选牌和 Chan 排序权限。
2. 修正回合开始结算，补齐双方互换视角的技能测试。
3. 加入 matchId/版本/幂等和开局确认，再做请求超时与断线收尾。
4. 统一 UI 更新队列、退出销毁及再战流程。
5. 加固 Worker 身份、限流、心跳与发布版本，再考虑更完整的重连。

## 8. 验证记录与后续验收

### 本轮已实施的修复

- `OnlineHostSession` 只向客机发送 `guestState`，不再把 `hostState` 放入开局包或普通状态包。
- `OnlineMatchHost` 增加协议版本、`matchId`、单调 `stateVersion`、动作白名单、阶段/决策校验和有界 request cache。
- `OnlineGuestSession` 提交 `expectedStateVersion`，对响应设置 12 秒超时，并拒绝旧版本或其他对局的快照。
- guest 投影保留客机自己的对手牌选择；Chan 5牌面只发送给当前行动者，排序弹窗也按行动权限创建和清理。
- 在线回合切换调用统一的 `turnStart('ai')`，先手为客机时补执行一次客机开局结算。
- UI 为事件 ID 增加跨批次去重；P2P 发送增加有界队列和 `bufferedAmount` 背压，信令断开时清理心跳。
- Worker 改为服务端生成 peerId，校验并重写大厅更新的发送者身份，增加 Origin、握手超时、消息字节上限和基础频率限制。
- 房间页重试连接复用已保存的昵称、房间号和信令地址，并把错误显示到当前页面。

这些改动仍保留“房主浏览器运行权威引擎”的产品边界：它们防止客机越权和意外泄露，不能防止房主自行修改本地代码。

### 后续验收矩阵

| 维度 | 最少场景 | 通过标准 |
| --- | --- | --- |
| 行动拥有者 | 房主/客机分别出牌、净化、排序、选对手牌 | 只有本人可交互，另一端不获得私有 choices |
| 角色/状态 | 双方先手；Chan、Moze、Otto 多步技能；中毒/灼烧/守护/飞翔 | 与规则一致，不漏算、不重复，不由 AI 替另一位真人决策 |
| 网络异常 | 延迟、重复包、旧包、关闭通道、发送异常 | 不重复扣牌/结算；不回退；等待有明确结束路径 |
| 开局与再战 | 延迟 ack、丢失首包、旧局消息迟到、动画中退出 | 双方进入同一局，旧任务不影响新局 |
| 私有信息 | 检查初始/普通/错误包及事件载荷 | 客机包没有房主手牌、未公开排序/选角内容 |
| 非法操作 | 无决策净化、越权 target、过期 cardId、非法颜色/排序 | 拒绝且状态完全不变 |
| Worker | 重复 ID、同房第三人、未 hello、超限消息、断线重连 | 身份和成员数正确，资源及时清理 |
| 真实双端 | 两个独立浏览器；跨 Wi-Fi/手机网络；强制信令回退 | 完整打一局并再战；可观察连接状态和错误 |
| 发布 | 两个不同 buildId、缓存旧 HTML | 不兼容时开局前阻止并提示刷新 |

优先给上述已复现问题增加会失败的回归用例，再实施修复。联机集成测试应检查完整发送包与实际按钮/弹窗，避免仅验证内部状态而漏掉玩家无法点击的问题。

## 9. 文档状态与发布边界

[功能清单](function_list.md) 和 [联机 README](../../online_game/README.md) 应与本报告一起维护。当前状态应明确区分：

- **已编码并有自动化覆盖**：客机私有快照、动作白名单与阶段校验、matchId/stateVersion、请求幂等、超时、Worker 身份与基础限流、事件去重。
- **已编码但仍需双机验证**：开局确认屏障、网络切换时的顺序、断线结束路径、真实 Worker 房间生命周期和所有角色技能矩阵。
- **架构限制**：房主浏览器仍掌握完整规则状态和随机数，不能作为竞技或有奖励场景的可信裁判。

发布前不要把“本地自动化通过”描述成“生产联机已验证”。静态资源、协议版本和规则版本应原子发布；线上验收至少覆盖两个独立浏览器、信令回退、刷新/断线以及旧页面阻断。
