# 在线对决延迟与卡顿分析

分析日期：2026-09-16。基于当前本地代码；本轮已按 P1/P2 优先项落地低侵入修复，但未进行生产网络压测。代码可以确认额外等待和重复工作，具体 RTT、帧率、包大小、耗时占比仍需要双端实测。

## 1. 结论与实施顺序

当前应优先减少“选牌的网络往返”和“动画串行等待”，然后解决动画队列竞争与传输恢复，最后根据测量结果优化快照和渲染。暂不需要更换整个联机架构；保留房主权威结算、访客私有快照和可靠传输。

| 顺序 | 问题 | 代码证据 | 建议 |
| --- | --- | --- | --- |
| P0 | 缺少分段性能数据，难区分网络慢与动画慢 | 会话没有 command RTT/播放积压统计；心跳仅发 ping | 先加入本地诊断指标 |
| P1 | 客机选牌需要往返，双击可能连续等待两次往返 | `hand_render.js` 先等待 `selectCard`，再执行 `doPlay/doDefend` | 本地选牌，提交原子出牌指令 |
| P1 | 多事件动画累加，播放期间禁止操作 | `events.js` 顺序 await；`controls.js` 全程动作锁 | 单次行动动画预算、并行反馈、决策优先 |
| P1 | 两套动画入口可能互相修改状态 | 在线 `_battleAnimation` 队列与 `_apiAction` 各自调用 `_consumeEvents` | 单一播放器、按版本提交状态 |
| P1 | 中继锁定后不升级 P2P | `send()` 一旦 relay，channel open 不改回 p2p | 有确认、有序号的安全切换 |
| P1 | 发送失败、超时后缺少可靠恢复 | 房主 `_broadcast()` 不处理 send 返回值；客机 12 秒后仅报错 | 同 requestId 重试、状态重同步、背压 |
| P2 | 全量快照及多次 JSON 深拷贝 | `online_match.js`、`online_session.js` 多层 clone | 先减重复投影/拷贝，再考虑增量 |
| P2 | 选中改变会重建手牌；背景逐帧调整画布尺寸 | `hand_render.js`、`particles.js` | 保留节点，仅更新样式；按 resize 调整画布 |
| P2 | 房主切后台可能暂停服务和展示 | 权威引擎在房主浏览器，动画依赖 rAF/定时器 | 检测可见性、恢复时同步及追帧 |

这里的优先级针对延迟优化。现有动作防重、版本校验、行动权限、隐私过滤都必须保留。

## 2. 当前一张牌的实际路径

普通客机操作：点击卡牌 → `selectCard` 发给房主 → 房主校验/投影/回传快照 → 客机选中渲染 → 点击出牌（或双击后续）→ `doPlay` 再发给房主 → 房主结算并回传快照和事件 → 客机顺序播放事件 → 恢复操作。

若没有预先选中，双击出牌需要选择与出牌两个串行请求。粗略耗时为：

`2 × 命令往返时间 + 两次房主处理/渲染时间 + 事件等待及动画时间`

预先已选中的出牌通常只需一次请求。此公式是路径分析，并非线上实测结果。房主自身出牌不需要请求往返，因此两端体感不对称。

重要区别：`OnlineMatchHost._drainEvents()` 已在房主内部推进事件门控结算；在线 session 的 `acknowledgeEvents()` 是空确认。因此当前不是“每个动画都向房主确认一次”，延迟主要来自动作往返和客户端播放排队。

## 3. 优先减少动画带来的等待

代码位置：[events.js](../../js/ui/events.js) `_playEvents()`、[controls.js](../../js/ui/controls.js) `_apiAction()`、[online_ui.js](../../online_game/online_ui.js) `_queueSharedBattleResult()`。

- `aiPlay` 在飞牌结束后额外等待 600 + 1400 ms；`playerPlay` 等待 400 + 600 ms。
- 判定展示另有 1200 ms 等待；多类伤害、buff、回复事件各自等待约 350–600 ms，部分提示达 1500 ms。
- `_playEvents()` 逐事件顺序执行，多效果技能会累加以上等待。网络即使很快，界面也可能几秒不能操作。
- 当前 fast 模式只将该函数中的 wait 缩短为 22%（最少 60 ms），不会自动缩短被调用动画函数自身的飞牌时长。
- `_apiAction` 与手牌交互检查 `_isHandlingAction/_isConsumingEvents`，不能简单删除锁，否则会重新引入连点错乱。

建议引入 `actionId` 及事件依赖分组：飞牌 → 判定（若有）→ 同步伤害/状态反馈 → 决策可操作。无依赖的血条、受伤闪光、buff 提示并行播放；同一次行动仍保留伤害和状态的正确先后关系。技能文字可持续停留供查看，不用让固定阅读时间阻塞下一步。

建议初始预算：普通出牌总展示约 400–700 ms，复杂判定约 800–1200 ms；这些是待验收的目标，不是硬性规则。净化、颜色、守护等需要输入的节点不能被跳过。先给在线模式独立配置，不全局改变单机节奏。

动画积压超过约 1 秒时进入追帧：压缩装饰等待、合并同一行动的反馈；不得丢弃权威动作、判定结果或待选择弹窗。切后台后恢复时以最新快照重建，不补播数十秒旧动画。

## 4. 本地选择与原子指令

代码位置：[hand_render.js](../../js/ui/render/hand_render.js)、[online_session.js](../../online_game/online_session.js)、[online_match.js](../../online_game/online_match.js)。

普通选牌/取消选中只影响自己的 UI，不需要立刻广播给房主和对手。将其保存为本地 `selectedCardId`，立即更新选中样式；点击出牌一次提交：

```json
{"method":"playCard","params":{"cardId":"..."},"requestId":42,"expectedStateVersion":105}
```

房主按 cardId 找到当前手牌，完成选牌与出牌的原子校验/执行。防御、弃牌确认、选择对手牌也可采用相同模式；排序和技能选择使用对应 `decisionId`。确认现有牌协议的 ID 在复制、交换和重连后仍稳定唯一，再依赖它，不能用会随抽弃牌变化的数组索引代替身份。

本地可以提前显示按下/提交反馈；伤害、随机判定、摸到什么牌仍等待房主确认。黑牌继续遵循“打出展示 → 选择颜色 → 效果执行”的产品规则，不为省请求擅自合并玩家必须做出的选择。

保留每位玩家一个在途权威指令。普通选中与悬停不占用此锁；收到新快照时清理已不存在的选中牌。不要通过允许多个基于同一版本的写指令并发来降低延迟。

## 5. 统一动画入口和状态版本

`_queueSharedBattleResult()` 用 Promise 链串行播放远端更新，但本地 `_apiAction()` 有自己的播放器入口。队列执行时还会将保存的 `result.state` 写入 UI；与此同时 `_consumeEvents()` 在播完后读取 session 最新状态。快速互相出牌时，这些入口可能跨版本读写同一界面，属于需复现验证的竞争风险。

建议所有来源统一进入一个 `OnlineBattlePresenter`（或现有 GameUI 内的一个协调器）：

1. 收包后立即验证并更新 authoritativeState，维持独立的 displayState。
2. 按 matchId、stateVersion、actionId、eventId 入队；同一事件只展示一次。
3. 只有播放器能写 displayState，禁止旧快照覆盖更高展示版本。
4. 不带事件且不涉及新决策的快照允许合并为最新一份；事件按因果顺序保留。
5. 离房/重新开局递增 sessionGeneration，并取消旧动画；await 返回后也要检查代次。

将“命令已确认”和“动画播放完成”分开记录；只有涉及当前行动必要动画/决策的锁阻止出牌，纯飘字不应锁住全部输入。

## 6. P2P、中继与恢复

代码位置：[p2p_adapter.js](../../online_game/p2p_adapter.js)、[worker.js](../../online_game/signaling/worker.js)。

当前使用可靠、有序 DataChannel；未打开时借 WebSocket 转发。`transportMode === 'relay'` 后 `send()` 不再使用 DataChannel，后续通道打开也不升级。这能避免两个通道交叉乱序，但可能让整局继续走中继。中继的实际速度取决于双方到该连接路径的延迟，不能假定 P2P 一定更快。

优化方案：

- 给 P2P 与 relay 分别加入应用层 ping/pong，测量 RTT 和抖动。现有 20 秒心跳只是到 Worker 的 ping，并没有覆盖“客机 → 房主 → 客机”的完整命令路径。
- 在双方确认、无在途命令的边界切换；引入 transportEpoch + 单调消息序号 + 切换 ACK。切换中缓冲必要消息，按相同 requestId 重试，不能重复执行动作。
- 当前 P2P 的 bufferedAmount 超过 256 KiB 直接返回 false，且不会在这个分支自动回退；房主广播忽略返回值可能导致客机一直等。增加有界发送队列、低水位恢复与显式失败处理。WebSocket 同样监测 bufferedAmount。
- 客机现有 12 秒超时不能解决“已执行但回包丢失”。使用原 requestId 重试，配合房主已有幂等缓存，并支持 requestState 重同步。状态落后时应重新校验用户意图，不能盲目重放旧索引。
- relay 对战包当前还广播回发送者，前端再丢弃自己的回包；可只转发给另一位成员，保留大厅 roster 的广播语义。
- Worker 当前限制单条入站消息 64 KiB、每连接每 10 秒 240 条消息。应统计包含 relay 外壳的 UTF-8 字节数，按需压缩字段或设计有界分包；不能单纯扩大限制来掩盖快照膨胀。
- 当前仅配置一个 Google STUN。记录 ICE 建连耗时、成功率和失败原因，实际测试中国境内不同网络；不能依据供应商名称判断可达性。仍不引入 TURN，保留现有 WebSocket 中继兜底。

本方案的核心优化不要求新增付费服务。中继流量与请求量仍计入现有平台用量；本文未核查当前套餐价格或承诺零费用。

## 7. 快照、主线程与画面

### 快照

每次成功操作（包括选牌）都会产生新版本与完整 guestState。`dispatch`、请求缓存、投影、session getState 和 UI 队列有多次 JSON 序列化深拷贝。开销可从代码确认，是否形成明显长任务仍需测量。

先消除不必要选牌请求；每版本缓存各自私有投影，在明确只读边界后减少重复 clone。记录每条包的字节数和 stringify/parse 时间，再决定是否引入 `baseVersion + patch + stateVersion`。增量失败必须能请求完整快照，不能将完整牌库/对手手牌作为性能捷径发给对方。二进制协议和压缩暂缓，避免先增加复杂度。

### 渲染

手牌已经存在 handRenderKey 缓存，不能称为“每次全页面重建”；但选中状态属于缓存键，改变选中会清空手牌容器、重建所有 Canvas 和事件监听。可保留按 cardId 索引的节点，选中与可出牌状态只更新 class/aria；卡面未变化就复用已有绘制结果。

背景粒子 `_initParticles()` 每帧设置 canvas.width/height，即使窗口尺寸不变也重置绘制缓冲区。移到 resize 回调，隐藏页面时暂停，保留相同配色和外观。当前仅 15 个粒子，须用实测确定其占比；不要直接删掉背景来“优化”。

飞牌已使用 transform，不需推翻实现。进一步批量读取布局后再写样式，减少交错 getBoundingClientRect；明确取消 rAF、临时卡牌及未完成 Promise 的生命周期。移动端可对粒子刷新率、同时飞牌数、像素密度设置可选档位。

### 房主后台限制

权威逻辑运行在房主标签页；房主后台/锁屏时若浏览器暂停页面，客机即使网络正常也可能等不到处理。显示“等待房主恢复”与网络断线的不同状态，恢复时重同步。短期保留当前架构；Web Worker 可以隔离部分主线程负载，但不能保证手机锁屏仍运行。若产品未来要求后台持续对战，再评估服务端权威引擎及对应成本。

## 8. 测量与验收

先加开发诊断面板和可导出的匿名汇总，不记录私有手牌。使用本机 performance.now() 计算本机时间差；不同设备时钟不能直接相减。房主将处理耗时随 ACK 返回，客机以本地发出/收到时间测完整命令 RTT。

| 指标 | 采集位置 | 初始验收方向（非当前实测） |
| --- | --- | --- |
| 点击到选中反馈 | 手牌点击/rAF | p95 ≤ 50 ms，本地立即响应 |
| 命令往返/房主处理 | session dispatch/receive、match dispatch | 各记 p50/p95/p99；剥离动画时间 |
| 收包到可操作 | receiveState、播放器决策节点 | 普通动作动画控制在约 700 ms 内 |
| 排队长度/最老事件年龄 | 单一播放器 | 连续操作不持续增长；超预算追帧 |
| 主线程长任务/帧时间 | 性能面板、支持时使用 PerformanceObserver | 定位 >50 ms 长任务；按设备比较掉帧 |
| 包大小/字节速率/缓冲 | 两种传输 send/receive | 不触发 64 KiB 限制；无无界积压 |
| 恢复正确性 | 超时、同请求重试、重同步 | 不重复出牌、不丢伤害、不回滚版本 |

测试至少包含：桌面同网、移动端同网、双方不同运营商、强制 relay、可用 P2P、房主切后台及恢复。网络模拟覆盖约 50/150/300 ms RTT、抖动、少量丢包及短时断线；这些是测试条件，不代表实际用户网络。

行为用例：连续搭桥、黑牌选色、净化提前完成、交换手牌、双方快速交替出牌、双击出牌、判定+回血+多 buff、超时后重试、动画未结束离房再开局。必须同时验证双方 HP/手牌数量/行动权一致，事件只播一次，私有手牌不泄露。

## 9. 可拆分交付

1. 指标 + 背景按需 resize + 选中节点复用：低侵入，先建立基线。
2. 在线单一播放器 + 动画预算 + 会话取消：解决“网络已到但画面仍等待”。
3. 本地选择 + 原子指令：减少客机串行往返，需要升级协议并覆盖双击/交换后的牌身份。
4. 发送背压 + 幂等重试 + 完整快照恢复，再实施安全传输切换。
5. 有数据证明负担仍大时再做增量快照/更多卡面缓存；达到目标即可停止复杂化。

## 10. 本轮已落地的修复

- 客机在进攻/防御阶段的选牌改为本地即时选中；真正出牌时发送一次 `playCard`/`defendCard` 原子指令，服务端仍按 `cardId + index` 校验当前手牌和合法性。传统 `selectCard`、`doPlay`、`doDefend` 继续保留给旧客户端和单机模式。
- 在线 UI 结果统一进入 `OnlineUI._queueSharedBattleResult()`，按 `matchId + stateVersion` 拒绝旧快照，并按事件 ID 跨批次去重；离开或重开对局会递增代次，旧动画完成后不会写入新界面。
- 客机指令沿用原 `requestId` 在短暂丢包时重试，主机广播遇到暂时性背压时保留最新快照重发；会话提供 `getDiagnostics()`，可读取 pending、重试次数和 RTT 分位数。
- DataChannel 背压时优先回退到现有信令中继，并在直连通道打开后从 relay 升级回 P2P；增加有界数据队列、低水位刷新和收发字节统计。中继迟到包不会把已建立的 P2P 再降级。
- 背景粒子画布只在窗口尺寸变化时调整尺寸，页面隐藏时暂停动画，避免每帧重置画布缓冲区；在线事件积压时缩短装饰性飞牌动画和等待时间，保留事件顺序及决策节点。

以上修复仍需按第 8 节的双浏览器、移动网络和强制 relay 场景验收；本地自动化通过不等于生产网络已验证。
